# A-005 userId-only 身份迁移

## 1 测试说明

范围：B1 运行时身份是否只依赖 `userId`，以及 V4 迁移后新表与旧表的数据一致性。
环境：本地 PostgreSQL（`foodmap_auth_db`）、Auth 服务 v4 迁移后启动、Gateway 8080。
测试数据：真实历史数据（23 个账号、48 条登录标识、31 条 Refresh Token），不做造数。
已知限制：只验证迁移与回填，不验证读取侧切换（尚未实现）；未覆盖并发写入新表。

## 2 用例设计

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| C1 | 新签发 Access Token 的载荷 | 只含 `tokenType/userId/expiresTime`，无 `accountId` |
| C2 | 身份绑定回填完整性 | `auth_identity_bindings` 行数 = 账号名 + 手机号 + 邮箱字段数 |
| C3 | 绑定无孤儿 | 不存在 `user_id` 在 `auth_accounts` 中缺失的绑定 |
| C4 | 会话回填一致性 | 会话状态与 `refresh_tokens.revoked_time` 推导一致 |
| C5 | 未回填 Token 可解释 | 缺会话的 Token 数量 = 账号缺失的 Token 数量 |
| C6 | 关键字段非空 | 会话的 `session_id`、`refresh_token_hash` 均非空 |

## 3 执行结果

| 编号 | 结果 | 证据 |
| --- | --- | --- |
| C1 | 通过：`payload 字段: tokenType,userId,expiresTime`，`accountId 是否存在: false` | 证据文件 §3 |
| C2 | 通过：`identity_bindings=48` = `expected_bindings=48` | 证据文件 §2 |
| C3 | 通过：`bindings_without_user=0` | 同上 |
| C4 | 通过：`session_status_mismatch=0` | 同上 |
| C5 | 通过：`orphan_tokens=9`，缺会话 Token 同为 9（账号 100001–100004 已不存在） | 同上 |
| C6 | 通过：空字段计数 0 | 自动化核验场景第 12–13 步 |

Flyway：`Migrating schema "public" to version "4"` → `Successfully applied 1 migration`，服务随后正常启动。
自动化：`node tools/verify/cli.mjs run harness/scenarios/b1-identity-migration.yml` → 通过 13/13。

## 4 未覆盖项与风险

- 新表只完成建表与回填，业务读取仍走旧表；真正的读写切换（含双写、灰度、回滚）未实现。
- 9 条孤儿 Refresh Token 无法定位 `userId`，保持原样；刷新时仍会因账号不存在返回 401。
- `identity_cipher`、`provider_subject`、`union_subject` 本轮为空，等第三方登录接入时再落地加密策略。
- 未覆盖并发注册产生重复绑定的唯一索引冲突。

## 5 结论

通过。运行时身份已只依赖 `userId`，新表结构与数据回填结果与旧表一致，可解释的差异只有历史孤儿 Token。读取侧切换作为后续任务另行跟踪。
