# A-006 认证写入双写与读取切换

## 1 测试说明

范围：注册、登录、退出登录是否在写旧表的同时写入 `auth_identity_bindings` 与 `auth_sessions`，以及迁移窗口期数据是否补齐。
环境：本地 PostgreSQL（`foodmap_auth_db`）、Auth 服务已应用 V5、Gateway 8080、Redis。
测试数据：真实历史数据 + 场景自动生成的 `zxq_dw_<epoch>` 账号（含手机号、邮箱）。
已知限制：只验证写入侧；读取侧仍是旧表。未覆盖并发注册碰撞、多端并发登录、Refresh Token 轮换。

## 2 用例设计

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| C1 | 注册后身份绑定 | 账号名/手机号/邮箱各 1 条，共 3 条 |
| C2 | 账号名绑定内容 | `identity_hash = sha256(lower(trim(name)))`、`primary_identity=1`、`verified=1` |
| C3 | 手机号脱敏 | `display_masked = 前3位****后4位` |
| C4 | 邮箱脱敏 | `display_masked = 首字母***@域名` |
| C5 | 登录后会话 | 存在 1 条 `session_id like 'sess-%'`、`status=ACTIVE`、`device_type=IOS` 的会话 |
| C6 | 登出后会话 | 该账号会话变 `REVOKED`、`revoked_time` 非空、无 ACTIVE 残留 |
| C7 | 全局一致性 | 绑定数 = 账号标识数；无账号缺绑定；无孤儿绑定/会话 |
| C8 | 未补会话的 Token | 数量必须等于账号缺失的 Token 数量（可解释） |
| C9 | 刷新语义不回归 | 刷新返回的 Refresh Token 与请求一致（不轮换） |

## 4 未覆盖项与风险

- 读取侧仍走 `auth_accounts`，新表是双写投影，切换读取需另立任务。
- 9 条历史孤儿 Refresh Token（账号 100001–100004 已不存在）无法补会话，保持原样。
- 并发注册撞唯一索引时对外可能表现为 500 而非友好冲突码。
- 退出登录事务内包含 Redis 拒绝名单写入，与「不要在数据库事务内调 Redis」基线轻微冲突，属既有行为。
- `device_type` 取注册渠道而非真实设备，多端场景不精确。
- **Refresh Token 轮换未采用**：实现期间发现唯一索引要求轮换才能同时保留旧会话撤销记录，但轮换会改变 F-003 已验收的接口契约（响应 refreshToken 变新值），因此回退为不轮换，会话保持 ACTIVE。
- `identity_cipher`、`provider_subject`、`union_subject` 仍为空，等第三方登录接入时落地。

## 5 结论

通过。注册、登录、登出三条写入路径已对新表双写，V5 补齐了迁移窗口期的遗漏，全局一致性 0 差异（除 9 条可解释的孤儿 Token）。读取侧切换不在本次范围。
